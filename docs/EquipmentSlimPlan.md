# 防具系统重构方案：从"数值叠加"到"单件机制 + 单位差异化槽位"

> 版本：v3（方向确认版）　日期：2026-11-18
> **v3 相对 v2 的根本修正**：v2 只减槽位（2→1），没解决核心痛点——流派效果全是**数值**，数值天生要靠"叠多件"才强，玩家一局凑不齐就永远成型不了。v3 做两件事：① 把流派效果从**数值**改成**单件即成立的机制**；② 槽位改为**单位特性差异化**（强单位少槽、成长单位多槽）。本稿未改游戏代码。

---

## 一、病根诊断（一句话）

**强度锁在"收集链条"的末端**：第一件只给流派信号（弱数值），要凑齐 2~3 件同流派堆数值才成型，但玩家一局根本拿不到 3 件 → 永远成型不了。

三句用户原话对应的机制事实：

| 用户痛点 | 代码事实 |
|---|---|
| "凑不齐三件" | 一局防具获取量少；套装阈值 `SET_THRESHOLD=2`（`SetBonusManager.gd:17`）已是硬门槛 |
| "第一件只是信号" | tier1 是弱数值（烈焰攻击+10%），单件穿上体感近乎为零 |
| "叠数件数值才成型" | `set_bonuses.json` 六个流派全是数值档（tier1→tier2），数值必然要叠 |

**结论**：只要流派效果是数值，就注定要叠；减槽位、调 UI 都治不了。必须换成"机制"。

---

## 二、核心设计一：流派效果 = 单件机制（穿上即成型）

### 2.1 六个流派机制表

每件防具自带一个**质变机制**，一件即完整生效，不依赖任何叠加：

| 流派 | 旧（数值，要叠） | 新（机制，一件成立） | 战斗层接线点 |
|---|---|---|---|
| 烈焰 | 攻击+10%→25% | 攻击**附带灼烧**（DoT，可叠层） | `CombatManager._apply_damage_with_effects` |
| 守护 | 防御+5→12 | 格挡时**反弹 30% 伤害** | `CombatManager` 受击/格挡分支 |
| 轮回 | 回血5%→10% | 击杀**回 2 点魂火** | 击杀结算（现"击杀+3魂火"死代码处） |
| 献祭 | 吸血8%→15% | 每回合扣 5% HP 换 **+20% 攻击** | `TurnManager` 回合开始 / `CombatManager` 攻击 |
| 灰烬 | 移动+1→2 | 移动后**留下燃烧地块** | 移动结算 / `TerrainManager` |
| 余烬 | 魂火上限+3→6 | 魂火耗尽时**下击必暴** | `SoulFireManager` + 暴击判定 |

> 具体机制数值是可调参数，上表为设计意图。**核心原则**：每条都是"一句话能说清、穿上就改变打法"的质变，不是 +X% 的数值。

### 2.2 三句话痛点如何被解掉

- **凑不齐三件** → 1 件就是完整机制；2 件是"双机制并存"（灼烧+反弹），永远不需要第 3 件；
- **第一件只是信号** → 第一件直接改变打法，穿上就会灼烧/反弹，HUD 立刻可见；
- **叠数值才成型** → 不叠数值了，多件是**横向多机制**，不是纵向堆数字。

### 2.3 品质 = 同一机制的强化，每一档都完整

```
烈焰 common    → 攻击附带灼烧（1 层）
烈焰 rare      → 灼烧 2 层
烈焰 epic      → 灼烧 2 层 + 灼烧可暴击
烈焰 legendary → 灼烧 3 层 + 可暴击 + 击杀引燃周围
```

common 也是"灼烧流"，不是半成品；legendary 是同一打法的完全体。品质梯度从"数值浓度"变成"机制厚度"。

### 2.4 配套系统去向

- **同单位 2 件套**：从"核心门槛"降为"同机制叠加厚度的彩蛋"（凑到同流派第 2 件，机制升一档）；不再是"没有就残废"。
- **tier2 质变硬门槛**（2件+epic）：取消，其效果并入 legendary 单件。
- **交叉套装**（4 组全队辅助）：保留，作为独立于单位 Build 的"队伍光环层"，不参与单件成型。
- **连通/方向**：与流派成型**彻底解耦**——连通只给纯属性微加成（现 +15% 上限），不决定"能不能吃到流派机制"；方向箭头不再是理解门槛。

## 三、核心设计二：单位差异化槽位（单位特性）

### 3.1 规则

| 项 | 规则 |
|---|---|
| 基准初始 | 第 1 天，平均单位 **2 槽** |
| 成长 | 每过一天 **+1**（第 1→2 天、第 2→3 天各一次） |
| Boss 战后 | **不加** —— 现有 `finish_cycle()` 已走 `finish_day(false)`（`GameState.gd:481-482`），天然满足，无需改 |
| 单位特性 | 部分单位初始槽位 **-1**（基础强壮）或 **+1**（成长/玩法多） |

### 3.2 设计意图：槽位 = "能同时开几个流派引擎"

配合"单件即成型"，槽位不再是"凑套装的门槛"，而是**这个单位能同时搭载几个流派机制**：

- **1 槽单位**（基础强）：单机制，靠本体高属性撑强度 → "朴实但硬"；
- **2 槽单位**（平均）：主流派 + 副流派，两种机制并存；
- **3 槽单位**（成长型）：第一天把三件喂满 → **三个机制同时开，开局即成型**——正是用户说的"第一天 if 防具都喂给它 build 就成型"。

这样不同单位的 Build 定位天然分化，玩家看到单位就知道"它是单核还是多核"。

### 3.3 建议的单位分配（可调）

依据现有 `unit_data.json` 的基础属性与转职分支丰富度：

| 槽位 | 单位 | 理由 |
|---|---|---|
| **1 槽**（-1） | `armored`（HP45/力9，bulwark）、`dragonborn`（HP45/力8/智6）、`axeman`（力10） | 基础数据强，本体即战力，不需要靠机制堆 |
| **2 槽**（基准） | `spearman`、`pegasus`、`archer`、`mage`、`cleric` | 标准成长曲线 |
| **3 槽**（+1） | `swordsman`（3 条转职分支含隐藏质变）、`mage`（法术连击+咒术双分支）、`cleric`（治疗+守护双分支） | 成长性与玩法多，适合喂满成型 |

> 上表为建议，最终哪个单位 +1/-1 由策划定。**落点**：`unit_data.json` 每个单位已有 `max_armor_slots` 字段（`UnitData.gd:100`，部分单位已写 2）——直接填 1/2/3 即可，无需新增字段。

### 3.4 关键代码修正点

| 文件 | 现状 | 改为 |
|---|---|---|
| `GameState.gd:453` | **硬编码** `unit_data.max_armor_slots = 2`，覆盖数据配置 | 从该单位数据读初始槽（开局时 `armor_slots` 按配置的 `max_armor_slots` 填充） |
| `GameState.gd:11` | 全局 `MAX_ARMOR_SLOTS_CAP=4` | 改为**按单位初始槽 + 2**（1→3、2→4、3→5），或提高全局上限到 5 并让 3 槽单位能到 5 |
| `GameState.gd:474-479 finish_day` | 统一 +1，受全局 cap 限制 | 保留 +1，但 cap 改为 per-unit |
| `UnitData.gd:100/302` | 默认 2、读档默认 2 | 默认仍 2（兼容），读档优先用存档值 |
| `MapScene.gd:155-176` | Boss 通关 `finish_cycle()`→`finish_day(false)` 不加槽 | **保持不变**（已满足需求） |

## 四、体验对比

| 维度 | 改前 | 改后（v3） |
|---|---|---|
| 流派生效 | 凑 2 件同流派才有，且是弱数值 | 单件即质变机制，穿上可见 |
| 成型链条 | 信号→叠 2~3 件数值→成型（常凑不齐） | 一件即成型；多件 = 多机制并存 |
| 玩家核心问句 | "能不能凑齐这套？" | "这件给哪个单位？开哪个流派？" |
| 槽位意义 | 凑套装的门槛 | 单位特性：能同时开几个引擎 |
| 单位差异 | 所有单位初始都是 2 槽，无区别 | 强单位 1 槽 / 平均 2 / 成长型 3 |
| 品质意义 | 数值浓度（common→legendary 数值递增） | 机制厚度（同一打法的完全体） |
| 理解成本 | 套装+tier2+交叉+连通多套交错 | 单件=机制，槽位=引擎数 |

### 连带影响

- **数值平衡**：机制型强度需整体回归，怪物血量/伤害可能要重配；
- **存档兼容**：老存档的防具 `modifier`（旧数值）需映射到新机制，或提供一次性迁移/清档；
- **自动配装评分** `_evaluate_layout`：套装/连通权重下调，单件机制匹配权重上调；
- **文档**：`GameplayDesignDoc.md` 防具/套装/槽位/竞技场章节全文同步。

## 六、风险与取舍

1. **六个机制要逐条接线并对齐竞技场**——这是最大工作量，也是最需要小步验证的部分。建议每做完一个机制就跑一遍战场+竞技场对照。
2. **Build 深度变化**：从"数值叠加的深度"变成"机制组合的深度"。前者是堆料，后者更有辨识度，但组合数下降——靠单位差异化槽位（1/2/3 槽决定机制数量）补偿。
3. **老玩家认知刷新**：套装、tier2、连通这些旧概念要重新说明，文档与 UI 引导需同步。
4. **"3 槽单位第一天成型"可能过强**：若测试发现碾压，可把 3 槽单位降到初始 2 槽+特殊成长，或压低其机制厚度。
