# 五系统过载诊断与极简方案

> 版本：v1　日期：2026-11-18
> 对象：箭头连通 / 防具套装 / 特技词条 / 遗物 / 光环
> 方法：三组子代理全文精读代码 + JSON 数据，以代码事实为准（设计文档可能过时）。本稿未改游戏代码。

---

## 一、结论先行

**过载不在"条目多"，在"五个系统抢同几个数值池，且大部分收益玩家看不见"。**

| 系统 | 规模 | 判定复杂度 | 收益可见度 | 过载程度 |
|---|---|---|---|---|
| 箭头连通 | 70%无箭头/30%带箭头，并查集分组 | ★★★ 几何谜题+4层倍率 | **数值完全不可见**（只在 print） | 最高 |
| 防具套装 | 6流派 tier1/2 + 4组交叉 | ★★ 三套口径并存 | 激活状态展示**口径错误**，交叉零UI | 高 |
| 特技词条 | 20词条/16类型，品质1~4条 | ★ 抽取逻辑最干净 | hover 完整可见 | 低 |
| 遗物 | 9个，4层生命周期 | ★★ 解锁5条路径+精炼 | 常驻被动无触发反馈，精炼数值不显示 | 中 |
| 光环 | 6个，3层生命周期 | ★★★ 研究→购买→使用 | 可见，但与遗物共用槽 | 中 |

**核心事实**：这五个系统最终都写进同一批共享字段——`buff_attack_percent`、减伤池（75% cap）、回血/吸血、魂火、复活——是**加算共享池**，不是独立轨道。五个系统往一个池子倒，玩家分不清"这一下 +10% 是谁给的"，还容易撞 cap 白堆。

## 二、逐系统诊断

### 2.1 箭头连通 —— 最该砍

- 方向 9 种枚举（`Direction.gd:19-29`），对接判定拆成 4 个函数（`ConnectedGroupCalculator.gd:116-137`）：斜线要求两端**同一枚举值且错开一行**，本质是几何谜题。
- 评分链 4 层：基础表（组2~6+ → 攻2~15%）→ 跨单位倍率（×1.3/2.0/2.5）→ 双箭头覆盖 → 组数倍率（×1.25/1.5）→ 双封顶 15%（`:179-220`）。**4 层乘法只换来一个最多 15% 的数**。
- **收益完全不可见**：+15%攻防血、+2护盾、+1魂火只出现在 `TurnController.gd:433` 的 `print()`；UI 只有黄框和"已链接 N 件"文字（`EquipmentConfigDetail.gd:131-135`），玩家不知道赚了多少。
- 僵尸代码：`Direction.gd:103-123` 的 `has_dir/has_diag_*` 全工程无调用。
- **复杂度与回报严重不成正比，是极简第一刀。**

### 2.2 防具套装 —— 口径混乱

- 三套判定口径并存：单位内 2 件（tier1，`SetBonusManager.gd:59-80`）、其中 1 件 epic+ 升 tier2（`:76-80`）、全队 4 组交叉（`:186-215`）。
- 数据层三套兼容字段（`effect/value`、`effects`、`tier2_effects`）并存，导出处靠兜底分支（`SetBonusManager.gd:108-114`）。
- **两个明确的正确性 bug**：
  - 自动配装评分用 `set_counts[tag] >= 3` 加分（`EquipmentConfig.gd:2915`），真实阈值却是 2——自动配置在优化错误目标。
  - 全队标签计数条按**全队**件数高亮"已激活2件套"（`EquipmentConfig.gd:495-527`），真实判定是**单位内**——玩家看到的激活提示可能是假的。
- 4 组交叉套装零 UI，效果（攻击%/HP/回血/击杀魂火）与其他系统全部重复。

### 2.3 特技词条 —— 最干净，别动它

- 24 天赋（5默认+19进度解锁，其中 9 个主动型 `active_*`）、20 词条/16 类型、品质给 1~4 条（`AffixManager.gd:8-13`）。
- 抽取逻辑简洁（两阶段：标签专属池→通用池，类型去重），hover 展示完整，是五系统里唯一"复杂度换到了可感知收益"的。
- 唯一问题：每种词条在战斗里各有一条读取路径（`CombatManager.gd` 8+ 处），竞技场又复刻一遍（`ArenaBattle.gd:715-733`）——是**实现重复**，不是设计过载。
- **保持不动，只做消费出口统一。**

### 2.4 遗物 —— 生命周期层数多

- 9 个遗物，解锁路径多达 5 条（默认/Boss按天/进度里程碑/事件/剧情，`RelicManager.gd:37-60`、`VictoryHandler.gd:406-414`、`ProgressUnlockManager.gd:70-85`）——语义重叠，progress 与 Boss 解锁重复。
- 4 层生命周期：局外解锁 → Boss后三选一（`RelicSelectUI.gd:20-44`）→ 占 4 格被动槽 → 150魂精炼（`GameState.gd:285-295`）。
- 精炼只有 5 个遗物有专属分支（`GameState.gd:404-413`、`TurnController.gd:200-211`），另 4 个付费无变化；精炼后的新数值 UI 不显示。
- effect 应用有 **4 份拷贝**（实战/编辑器/模拟器/竞技场）。
- 常驻被动战斗中无专属触发反馈，玩家不知道"首击必暴"是遗物给的。

### 2.5 光环 —— 与遗物高度同构

- 6 个光环，3 层生命周期：魂研究（100-150魂/2-3天，`AuraManager.gd:28-30`）→ 魂火购买（4-8，`GameState.gd:544-554`）→ 战场点击释放（用完即毁）。
- 效果 6 种，与遗物/套装/词条**全部重叠**（攻击+/减伤/击杀魂火/击杀回血等）。
- 回合钩子 2 份且 1 份死代码（`TurnController.gd:442-459` 无调用；`TurnManager.gd:223-239` 是唯一生效的）。
- 槽满时无替换流程，直接卡死提示"需先卸下"（`EquipmentConfig.gd:1224-1232`）——交互不如遗物完善。

## 三、极简方案（分三档，可独立采纳）

### 极简档 A —— 零体验损失的清理（强烈推荐，先做）

这些是纯删除重复/死代码/bug 修复，玩家体验不变甚至变好：

| 动作 | 落点 | 收益 |
|---|---|---|
| 删光环死钩子 `_apply_turn_start_auras` 一份 | `TurnController.gd:442-459` | 减一份重复逻辑 |
| 遗物 effect 应用合并为单一函数，4 处复用 | `TurnController/GameDataEditor/BattleSimEngine/ArenaBattle` | 减 3 份拷贝 |
| 删连通僵尸代码 `has_dir/has_diag_*` | `Direction.gd:103-123` | 减认知负担 |
| 修自动配装阈值 `>=3` → `SET_THRESHOLD` | `EquipmentConfig.gd:2915` | 修 bug |
| 修标签计数条按单位统计 | `EquipmentConfig.gd:495-527` | 修假激活提示 |
| 三选一池不足静默降级为二选一/一选一 | `RelicSelectUI.gd:37-38` | 减警告刷屏 |
| 统一加成消费出口为 `BuildEffectResolver` | 四个消费文件 + 竞技场 | 修"有的相加有的max"口径分裂 |

### 极简档 B —— 砍掉"付出复杂度但无回报"的系统

| 动作 | 落点 | 体验代价 |
|---|---|---|
| **删交叉套装 4 组** | `set_bonuses.json:86-119` + 4 处消费分支 | 接近 0（零 UI，效果全重复） |
| **砍连通数值层，保留视觉层**：连成组→固定 +1 护盾，删两层倍率与封顶 | `ConnectedGroupCalculator.gd:159-220`、`TurnController.gd:417-431` | 低（收益本就不可见） |
| **精炼改数据驱动**，9 个遗物都能精炼且 UI 显示新值 | `GameState.gd:404-413`、`TurnController.gd:200-211` | 正向（原来 4 个付费无收益） |

### 极简档 C —— 结构性合并（动内核，收益最大）

**光环并入遗物**——代码事实支持，且改动 90% 在数据+UI，战斗层几乎不用动：

- 引擎侧 `TurnController.gd:138-224 apply_team_buffs()` 本就把「遗物→光环→词条→套装→连通」当同类顺序处理。
- 两者共用同一 4 格被动槽（`PartyState.gd:123-166`），最终写同一批字段。
- 唯一实质差异是生命周期：遗物常驻+精炼，光环研究+购买+一次性释放。

具体做法：
1. `auras.json` 6 条并入 `relic_data.json`，effect key 统一；
2. 删三态研究（`AuraManager.gd` 研究/加速、`AnvilTavern.gd:138-200`），改走 `ProgressUnlockManager` 现成的进度解锁；
3. 局内统一三选一获取、常驻生效；
4. 一并删：研究 UI、`active_auras` 字段及三处钩子、战场"释放"交互、魂火购买链路。

**代价**：失去"选定时刻释放光环"的局内爆发，和 FORGE 的魂火消费口（4-8魂火）。折中：保留"一次性遗物"子类，而非独立 Manager+研究系统。

> 注：档 C 与 `EquipmentSlimPlan.md` v3 的"流派改单件机制"是两条独立线，可并行评估，但都属结构性改动，建议分别做样板验证。

## 四、推荐路线

1. **先做档 A**（半天量级，零风险）——顺手修掉两个 UI 假提示 bug，玩家立刻觉得"准了"。
2. **再做档 B 的交叉套装 + 连通数值层**——这两块付出最多复杂度、回报最少，砍完系统立刻清爽。
3. **档 C 与 v3 装备重构一起评估**——都是结构性改动，等前面验证完再决定要不要动内核。
4. **自始至终别碰词条设计**（只统一消费出口）——它是唯一健康的系统。
