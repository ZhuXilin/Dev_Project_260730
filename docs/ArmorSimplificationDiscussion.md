# 方案 A · 执行清单（准备做，纯 UI 零数值风险）

**目标**：玩家看到防具就知道"干嘛的、怎么合并"，不动任何数值/规则/存档。

### A1. 统一防具说明（消除两套口径打架）
- 现状：Roll 卡已是好设计（流派色徽标 + 【流派】Lv≤cap + 机制一句话，`ArmorRollUI.gd:308-338`）；但老装备界面 hover 仍显示 v5 的防御/属性/连通组/词条列表/套装说明（`EquipmentConfigDetail.gd:136-164,257-270`）。
- 改法：老装备界面 hover 改用同一套 v6 格式——**流派色 + 品质 + 一句话机制**；删掉 v5 连通组（v6 已移除该机制）、词条列表、套装说明三块。
- 保留：防御数值（真实影响 `CombatManager:166`）。

### A2. 合并决策前置显示
- roll 卡（`ArmorRollUI.gd:335`）在"落位动作"处，对每个单位头像预先算出结果并标注：
  - 同流派 → "并入 → Lv2/Lv3（上限 Lv3）"
  - 新流派且空槽 → "觉醒 Lv1"
  - 槽满 → "覆盖 → 删除 N 件旧防具"
- 依据：`BuildManager.apply_armor`（`:413-453`）的决策树；`QUALITY_CAP`（`:75`）；`overwrite_school`（`:462-483`）确实会删 armor_slots 中该流派所有防具。
- 覆盖确认框（`ArmorRollUI.gd:542-546`）文案从"原机制将消失"改为"将删除 N 件旧防具 + 清空该流派机制"。

### A3. 词条收进折叠详情
- 默认视图不显示 20 词条列表；加"详情"展开按钮，想深究再看。
- 词条 tag（如「焚身[烈焰]」）**全部隐藏**——它不参与共鸣，显示只会误导（`AffixManager.gd:70-88` 仅抽取池用）。

### A4. 假提示修复（一行级）
- 装备界面标签计数条按**全队**统计却 tooltip"已激活 2 件套"（`EquipmentConfig.gd:452-484`），而真实套装判定是**单位内**（`SetBonusManager.gd:59-80`）。改为按单位统计。

### A5. 死代码清理
- `reforge_school` / `get_reforge_cost`（`BuildManager.gd:908,1039`）零调用（重铸已移除），删除。
- 500G"锻造"实为重掷词条（`EquipmentConfigForge.gd:244-251`），改名为"重铸词条"避免和已移除的重铸流派混淆。

**A 的改动面**：4~5 个文件，纯展示与文案 + 死代码，不碰数值/存档/规则。风险极低。

# 方案 C · 深度评估（砍词条系统）

## C 的真实定义
"每件防具 = 1 流派机制 + 1 数值词条，词条池缩到 5~6 个"。**核心矛盾：20 个词条承载了六流派的全部乘区**（暴击、穿透、吸血、反击、治疗、回魂火）。砍掉 14 个不是"减负"，是**删掉半个战斗系统**。

## 数据链路（改造必动处）
| 项 | 现状 | C 下的改动 |
|---|---|---|
| `affixes.json` | 20 条，`min_quality` 分档 | 保留 5~6 条 |
| `AffixManager.gd:8-13` | 品质挂 1/2/3/4 条 | 全改 1（与"每件1词条"一致） |
| `DataValidator.gd:29-34` | 17 种 type 白名单 | 同步删减 |
| `set_bonuses.json` | tier2 含暴伤/吸血等 | 需接收被删乘区的补偿 |
| 存档 | `affixes` 原样存 id/value，无校验（`SaveManager.gd:362-367`、`UnitData.gd:402-407`） | 老存档死 id 静默失效 → 按项目既定口径「不兼容老存档」，不做过滤/映射 |
| `item_data.json` | 50 件全 armor，tag 承载流派机制 | **不用改**（套装/熔合走物品 tag，`SetBonusManager:59-71`、`ItemManager:143-155`） |
| 锻造/合成 | 调 `roll_affixes`/`create_instance`，不硬依赖多词条 | 改 count 后自动适配 |

## 数值影响（C 的最大成本）
被删词条是**乘区**，不是小数值：
- crit_damage 0.10~0.25、crit_chance 0.03~0.08、双穿透 0.05~0.10
- anti_crit 0.20~0.40、lifesteal 0.05~0.15、counter 0.15~0.40
- heal_boost 0.15~0.30、turn_regen 0.01~0.06、soul_fire_gain +1

**后果**：烈焰（暴击/穿透）、守护（抗暴/反击）、献祭（吸血/治疗）、轮回（回血/穿透）四条流派的核心乘区全部失去载体，只剩流派机制的基础数值。若不补偿，Build 深度直接退回"只有六流派主动技能"——这正是用户之前要求的"加强 build 深度"的反方向。

**补偿方案**：把乘区并进保留的 5~6 个词条（如一个"锋锐"同时给攻击+暴击）、或并进套装 tier2、或并进流派机制本身（提高 Lv 基础值）。无论哪种，都要重新跑数值平衡——`BattleSimEngine.gd` 可辅助。

## 三种 C 的变体（按代价排序）

| 变体 | 做法 | 收益 | 代价 |
|---|---|---|---|
| **C1 保守** | 20→10 词条，保留全部乘区类型，删重复的纯数值（如 3 个 hp_flat 合 1、2 个 turn_regen 合 1） | 列表短一半，认知负担降 | 小：改数据 + 品质挂数从 4 降到 2，数值基本不损 |
| **C2 激进** | 20→6 词条，乘区并进流派机制（每个流派自带 1 个乘区），词条只留纯数值 | 最简洁，"防具=流派"一眼懂 | 大：重写 4 流派数值口径 + 套装重平衡 + 存档清洗 + 回归测试 |
| **C3 重构** | 彻底砍词条层，防具只有流派机制 + 品质决定机制 Lv 上限 | 极简 | 极大：等于重做装备系统，战斗里所有 `get_affix_value` 分支要改，存档结构变 |

**注意**：真正解决"看不懂"的是 A；C1 只是"列表短一点"，C2/C3 是在用系统重做换简洁，且 C2 的乘区内并会削弱"词条自由搭配"的 build 表达性——与用户强调的 build 深度相悖。

## 我的判断
- **C1 可做**：本质是 A 的数据侧补充，风险可控，能顺带减少"20 条要看"的负担。
- **C2/C3 不建议**：代价是删掉六流派乘区与 build 表达性，收益 A 已能拿到大半。除非用户明确想重做装备系统，否则不值。
- 顺序建议：**先做 A**（零风险验证"一眼懂"是否解决痛点）→ 试玩后若仍觉得词条多，再做 C1（保守减到 10 条）。

### C1 · 词条 20→16（乘区全保留）
**重要前提更正**：实施前逐条 grep 确认原 20 词条**全部生效**（crit_damage/lifesteal/counter/heal_boost/双穿透/soul_fire_gain/turn_regen 等乘区都在战斗结算读取），"只有3类生效"的早期判断是错的。因此 C1 不能简单按"删纯数值"压到 10 条——16 种 type 需至少 16 条才能保住全部乘区。

**做法**：`affixes.json` 按 type 去重，20→16 条：
- 删 4 条重复纯数值：`affix_defense`（坚硬）、`affix_hp`（坚韧）、`affix_blood_pact`（血契）、`affix_cycle_regen`（轮回 3-6）
- 数值等量补偿：余温(hp_flat) 3-6→3-8（吸收坚韧/血契上限）、灰烬护体(defense_flat) 2-4→1-4（吸收坚硬下限）、点滴(turn_regen) 1-2→1-6（吸收轮回 3-6）
- 多 tag 补覆盖：灰烬护体 tags 加「守护」、余温 tags 加「献祭」——确保每个流派都有 common 品质专属词条（原方案会让余烬/献祭低品质池断裂）
- `AffixManager.QUALITY_AFFIX_COUNT` 1/2/3/4 → 1/2/2/3（梯度温和收缩）
- **不做老存档兼容**（项目既定口径：不兼容老存档、直接用新版本）。删除的 4 个 id 在新存档中不会出现；若加载旧档含这些 id，词条会静默失效，属预期行为。

**未动**：`item_data.json`（50 件防具的流派由物品 tag 承载，不受影响）、套装/熔合（走物品 tag）、`DataValidator` 白名单（16 type 全覆盖，无需改）、锻造/合成代码（自动适配新条数）。

### 校验
- 16 条 / 16 种 type，DataValidator 白名单全覆盖；每流派 common 专属池：灰烬2/守护2/轮回1/献祭1/余烬1（烈焰原本为0，走通用池，维持原设计）。
- 涉及 10 个脚本 gdtoolkit 解析全通过，affixes.json 合法。

4. 锻造按钮改名后入口仍可用。
