# 装备极简流程设计 ·「意图式配装」

> 版本 v1 · 2026-11-18 · 目标：把"配装计算"变成"做选择"，从购买到装备一键完成，选完立刻回战斗。
> 承接文档：`EquipmentSlimPlan.md`（机制流派 + 单位差异化槽位）、`SystemOverloadAnalysis.md`（五系统过载诊断）。
> 本轮只做设计，不改游戏代码。

---

## 0. 一句话定位

> **玩家表达意图（"这单位走烈焰"），系统执行细节（摆位/对方向/算连通/核价）。**
> 决策权在玩家，计算量归零。这不是自动配装——自动配装是系统替你选最优解、玩家零决策。

分辨标准：

| | 谁做选择 | 玩家感受 |
|---|---|---|
| 自动配装（不要） | 系统算最优，玩家点一下 | "被安排了，没我什么事" |
| 意图式配装（本方案） | 玩家定流派/给谁，系统跑腿 | "我做了决定，而且立刻生效" |

---

## 1. 核心转变：三个"从……到……"

| 维度 | 从 | 到 |
|---|---|---|
| 装备性质 | 一张要填写 6 个维度的表单 | 一句人话的机制卡（"攻击附带灼烧"） |
| 成型方式 | 横向凑套（同流派 2 件才触发） | 纵向升级（第 2/3 件并入第 1 件，逐层变强） |
| 操作流程 | 购买→比较→拖拽→选槽→对方向→凑套→洗词条（8 步） | 三选一→点单位（看一句话后果）→完成（2 步） |

---

## 2. 新机制：觉醒 + 并入（核心）

这是解决"第一件只是信号、凑不齐三件"的关键设计。

### 2.1 规则

- 每件防具 = 一个**流派核心**，携带一个流派 + 一句机制描述（机制流派见 `EquipmentSlimPlan.md` v3）。
- **第一件同流派装备**装到单位身上 → **觉醒**：该单位获得该流派完整机制（烈焰 = 攻击附带灼烧 Lv1）。
- **第 2/3/4 件同流派装备**再获得 → **自动并入**同一个机制，把它的等级往上推（Lv1→Lv2→Lv3→Lv4），**不占新槽、不另起一套**。
- 品质决定这个机制的**层数上限**：common 上限 Lv1、rare Lv2、epic Lv3、legendary Lv4。品质越高，能堆的层数越多——但每一档从第 1 件起就是完整可用的机制，不是半成品。

### 2.2 为什么它解决了老问题

| 老问题 | 新机制怎么解 |
|---|---|
| "凑不齐三件" | 不需要凑。每件同流派装备都喂给同一个机制，1 件也能玩，3 件只是更强 |
| "第一件只是信号" | 第 1 件直接觉醒完整机制（穿上就灼烧），不是光给个标签 |
| "要叠数件数值才成型" | 叠的是**同一条机制的等级**，每次并入都有可见的即时反馈（Lv↑、灼烧更痛），不是抽象数值 |
| "6 流派 × 4 品质 = 24 格，池子稀释" | 玩家只认 6 个流派身份，品质退为层数上限的背景信息 |

### 2.3 与 v3 方案的关系

v3 的"机制流派 + 单位差异化槽位"保留为本方案的**战斗内核**：
- 六流派机制（灼烧/反弹/击杀回魂火/扣血换攻/燃烧地块/耗尽必暴）不变。
- 单位初始槽位 1~3、每天成长、boss 战后不加——不变。
- 本方案新增的是**流程层与整合层**：觉醒/并入 + 一键归属 + 系统裁剪。

## 3. 一键流程（购买→装备）

### 3.1 玩家看到的

进入商店/三选一/宝箱，屏幕上只出现**三个流派核心**，每张卡上写：
- 流派名 + 一句话机制（"攻击附带灼烧"）
- 品质角标（决定层数上限，非数值浓度）
- 归属预览：给每个单位会触发什么（"给剑士=新觉醒烈焰 / 给守卫=并入烈焰 Lv2"），见 §4

### 3.2 玩家做的

1. 选一张卡（偏好判断：这局我想让队伍更偏火 / 更偏守护）。
2. 点一下目标单位——系统用一句话说清后果："觉醒新流派"或"并入已有流派升 Lv"，玩家一眼决定，无需算数值。
3. 完成，回战斗。

### 3.3 系统秒做的（玩家无感）

- 自动落到该单位下一个空槽，无需玩家选槽位。
- 方向自动生成并自动对齐（或直接取消方向，见 §5）。
- 连通组、套装、词条加成在后台按现有管理器计算，结果即时生效。
- 若并入的是同流派已有机制 → 自动升级层数，旧装备不产生"替换/丢弃"提示。
- 若目标槽满 → 明确提示"该单位流派槽已满，要不要并入现有机制 / 换人"。

### 3.4 代码落点（已核对）

| 环节 | 现有接口 | 说明 |
|---|---|---|
| 商店卡片生成 | `EquipmentConfigShop.gd:99` `_create_item_button()` | 已按流派色块 + 价格构建，改造为三选一卡片 |
| 购买+装备 | `EquipmentConfigShop.gd:157` `buy_shop_item()` | 当前要求 unit_idx+slot_idx 并校验；改为"选中单位即装备"，内部自动选空槽 |
| 单位防具槽 | `UnitData.armor_slots`、`GameState.gd:453` | 槽位数据现成，per-unit `max_armor_slots` 字段已在 `unit_data.json` |
| 流派机制 | `set_bonuses.json` + `SetBonusManager.get_unit_set_effects()` | tier1/tier2 效果现成，下沉到单件觉醒/层数 |
| 连通/词条后台 | `ConnectedGroupCalculator` / `AffixManager` | 保持后台计算，只从 UI 移除 |

## 4. 保留"选择感"的关键：每局流动的流派身份（不固化）

一键不能变成无脑，但选择感**不能靠永久固化换来**——那等于开局就把答案写死，每局打同一套，违背肉鸽的根基。

**核心：单位没有预设流派。谁是烈焰、谁是守护，完全由玩家每局当场决定，重开一局全部归零重来。**

### 4.1 唯一的选择：这件给谁

装备卡对每个单位给出**一句话后果预览**，玩家的决策就是读这句话做取舍：

| 目标单位当前状态 | 装上这张烈焰卡 | 玩家看到的提示 |
|---|---|---|
| 空 / 无烈焰机制 | 觉醒新流派 | "剑士 → 觉醒烈焰（攻击附带灼烧）" |
| 已有烈焰 Lv2 | 并入升级 | "剑士 → 烈焰升至 Lv3" |
| 已有别的流派（守护） | 开第二流派（占第 2 槽） | "剑士 → 新增守护反弹（主流派仍烈焰）" |

这就是**选择**（要专精一个单位，还是给另一个单位开新流派），不是计算（不用比数值、不用凑条件）。

### 4.2 新鲜感从哪来

- **身份每局重掷**：上一局剑士是烈焰，这一局你可能给他守护——同样的单位，不同的打法。
- **三选一随机**：每局商店/掉落给的流派卡不同，逼你临时改构筑方向。
- **首个单位词条**：仍保留 v3 的单位槽位差异（强单位槽少、成长单位槽多），但这是**结构差异而非流派绑定**——槽多的单位能同时开更多流派，给玩家"这局要不要喂它"的临时决策。
- **可选软倾向（非惩罚）**：若要一点引导，可用"每局开临时赐福"——每局随机 2 个流派本局 +1 起始层数，重开即变。这是**局内随机 buff，不写进单位数据、不带到下一局**，既有新鲜感又不固化。

### 4.3 明确不做

- 不在 `unit_data.json` 写死 `affinity` 字段。
- 不做"非本命 -1 层数"之类的永久惩罚——那会把玩家锁回固化路线。
- 单位差异只保留"槽位数"这一结构属性，流派身份 100% 交给每局选择。

## 5. 系统裁剪清单（极简删除）

承接 `SystemOverloadAnalysis.md` 的诊断，按"玩家是否需要做决策"分类：

| 系统 | 处理 | 理由 |
|---|---|---|
| 方向 / 箭头连通 | **从玩家层移除**：方向自动生成并对齐；连通收益后台算或砍数值层只留黄色连线反馈 | 几何谜题，收益不可见，无决策价值 |
| 2 件套 / 交叉套装 | **移除**：改为单件觉醒 + 重复并入 | 凑不齐是死结；交叉套装零 UI、效果重复 |
| 词条重洗 / 锻造 | **移除玩家操作**：词条固定、出生即定、所见即所得 | 盲盒 + 计算，与"不做算术"冲突 |
| 熔铸 / 合成 | **并入机制**：作为"并入升级"的一种入口，产出即升级，不再产生新物品 | 减少物品条目 |
| 遗物 + 光环 | **合并为"单位被动"**，跟随单位，购买/解锁即得 | 两系统同构、收益不可见，合并省一套 UI 和生命周期 |
| 品质 | 退为**机制层数上限**的背景信息，卡片角落标出 | 保留梯度感，不参与玩家决策 |
| 商店刷新 / 价格比较 | 保留但**弱化**：三选一内比价，不跨页比 | 三选一是有限选择，不是无尽搜索 |

## 6. 潜在的"新机制"备选（可选，不必一次做完）

若担心极简后深度不足，可从中挑一个补回策略性，但都遵循"选择而非计算"：

| 备选 | 做法 | 为什么不破坏极简 |
|---|---|---|
| **魂火喂养** | 花魂火直接把某流派机制 Lv+1，替代再找一件装备 | 一个按钮、一个资源，决策是"喂哪个流派" |
| **转职/洗点** | 允许把单位已并入的机制折算成魂火，改走别的流派 | 低频操作，不进日常循环 |
| **共鸣里程碑** | 单机制到 Lv3/Lv4 触发世界观事件 + 战力质变 | 给玩家"我做成了"的高光，非数值计算 |
| **混搭反噬** | 同单位两流派都到 Lv2 触发特殊"混沌"效果 | 老玩家的反向构筑，可选 |

## 7. 代价与风险（说清楚）

- **Build 深度下降**：从"六维排列"降到"选流派 + 选给谁"，这是极简的必然取舍，靠机制差异 + 每局流动的身份决策 + 魂火联动补回。
- **数值配平重做**：把套装/连通/词条的强度转移到"觉醒机制 + 层数"，需要逐流派重配；竞技场 `ArenaBattle` 必须同步对齐。
- **存档兼容**：老存档的 2~4 槽 + 散件要迁移为"机制 + 层数"结构。
- **工作量集中**：战斗层六流派机制接线（`CombatManager`/`TurnController`/`SoulFireManager`/`EnemyAI`）+ 竞技场对齐 + UI 三选一重构。

## 8. 建议实施顺序

1. **阶段 A · 样板**：只做烈焰一个流派，跑通"觉醒 + 并入 + 一键归属 + 竞技场对齐"，验证机制形态与手感。
2. **阶段 B · 铺开**：其余五流派机制接入；槽位差异化落地（`GameState.gd:453` 硬编码去掉，读 `unit_data.json`）。
3. **阶段 C · 裁剪**：按 §5 逐步删除方向/套装门槛/词条重洗，遗物光环合并。
4. **阶段 D · 补深度**：从 §6 挑 1~2 个新机制补回策略性。
5. 全程同步 `GameplayDesignDoc.md`、`GameplayAnalysis.md`、工作日志。
